## 做得好的部分

- Employee、Task、EmployeeManager、TaskManager、Scheduler 职责基本清楚，代码容易阅读。
- 按技能建立优先队列，选择当前低负载员工；顺序执行时，分配后会刷新员工的所有技能队列。这是合理的在线贪心策略，不要求全局最优或预知未来任务。
- 成功分配会同步设置任务的 assignee 和 ASSIGNED 状态；工作量可查询，报告可展示任务及负载极值。
- AtomicInteger 保证负载增量不丢失；按键 compute 保护同一技能的 poll 和同一员工任务列表的写入，体现了局部并发控制意识。
- 原有 25 项测试全部通过，覆盖技能匹配、顺序负载选择、状态更新、并发累计和任务记录。

## 关键问题

### 1. 多技能队列与负载更新不在同一个一致性边界

位置：`EmployeeManager.assignemployee`、`requestEmployee`、`Employee.compareTo`。

同一 Employee 被放入多个 PriorityQueue，比较依据是可变的 load。assignemployee 先增加 load，再逐个技能 remove/add；ConcurrentHashMap 的 compute 只协调单个键，不能使整个过程原子化。

确定性复现：shared 具备 A/B，负载为 0；lower 具备 B，负载为 5。从 A 取出 shared，将其负载增加至 10，在刷新技能队列前暂停。此时请求 B，实际返回 shared（10），而不是 lower（5）。B 的堆仍保留旧顺序，直接影响工作量均衡。评审测试通过 latch 固定此交错，不依赖随机压力测试。

此外，addEmployee 的 ArrayList 写入和 PriorityQueue.offer 未与其他访问统一协调；TaskManager.getTasksByEmployee 在 compute 之外复制可变 ArrayList，并发读写没有完整保护。若约定初始化后不再加员工、全部调度结束后才查询，应明确说明；Team.main 确实按这一生命周期运行。这些限制仍不能消除上述调度过程内的跨技能竞态。

### 2. 异常包装没有恢复状态

位置：`Scheduler.scheduleTask`。

- requestEmployee 已 poll 员工，若 assignemployee 抛异常，调度抛 ScheduleException，但员工没有归还。只有一名 A 技能员工时，之后 requestEmployee("A") 返回 null。
- assignemployee 已增加负载，若 taskManager.createTask 抛异常，调度失败却留下负载。评审中任务负载为 3，失败后员工负载实际为 3，任务记录为空。

两项通过重写现有公共方法注入异常验证；它们说明当前 catch 所表达的失败契约不完整，不意味着普通内存写入必然发生此异常。相比正常并发调度缺陷，这属于次要但明确的一致性问题。包装异常也丢失了原始 cause。

### 3. 领域状态的修改权限过宽

Employee.getLoad 返回内部 AtomicInteger，调用者可直接改值而不刷新优先队列；员工技能集合只在读取时复制，构造时仍保存外部集合引用。调用者后续改变原集合会造成技能模型与索引不一致。

Task 的员工和状态可以分别任意设置；同一 Task 重复提交会重复累计负载及记录，甚至出现在多个员工的列表中，而任务自身只保留最后的 assignee。题目没有明确重复提交契约，因此这是需要补充的接口规则，不把它当作题目硬性要求。正工作量、null skill、整数溢出等输入边界也应给出校验或前置条件。

### 4. 现有并发测试验证的范围有限

5000 次调度测试检查成功任务不丢失、负载累计正确，允许竞争时出现 No available employee；它没有证明所有有匹配技能的任务都被接受，也没有验证每次选择都是最低负载。

当前 poll/归还模型会让唯一匹配员工被短暂取出时的重叠请求失败。题目没有规定等待或重试语义，因此不单独作为硬性扣分项，但应明确这是接口行为。原有失败测试只检查抛异常或未记录任务，漏掉了员工归还和负载恢复。

## 分级依据与改进方向

基础建模、数据结构选择、正常流程和局部并发处理足以支持 Junior 培养门槛；跨队列排序、失败恢复和封装仍需辅导，尚不足以支持 Senior 的独立正确交付。Staff / Principal 所需的统一状态规则和清晰接口契约也未建立。没有完成时长、沟通或独立性证据，不推断这些能力。

优先为“选员工、更新负载、登记任务、更新任务状态”建立统一提交边界。在本题规模下，单锁下扫描匹配员工并完成分配，是容易解释和验证的方案；不必为了保留堆引入复杂锁协议。查询快照也应采用相同协调规则。随后收紧 load 和任务状态修改权限，构造时复制技能集合，声明输入及重复调度规则，再补充对应回归测试。

本轮未修改生产 Java 或原有测试。适配已有独立评审测试的 Task 构造器，并添加 Maven reviewer profile，验证记录见 [TESTS.md](../TESTS.md)。
