## 主要问题

### 1. 同一任务的并发防重缺少统一边界

EmployeeManager 在锁外检查 Task.status，锁内只预占员工负载，稍后 TaskManager 才设置任务状态。两个请求可能同时通过 PENDING 检查并选择不同员工；TaskManager.compute 按员工键协调，不能保护这两个请求共享的 Task。Task.assignTask 内的检查和字段写入也未同步，因此存在双重登记和任务归属不一致的交错风险。

这是代码审查结论，本轮未用独立测试确定性复现双重登记。顺序重复提交已验证正确，不再当作缺陷。若支持同一任务并发提交，应为任务建立原子的提交/防重边界，并用固定交错测试验证；若接口只支持每个任务单次并发调用，应明确约定。

### 2. 补偿仅恢复负载，登记后的失败契约未定义

登记前抛异常时，Scheduler 能恢复预占负载，且不会在员工选择失败时误扣。已修复的问题不再扣分。

但如果扩展的 TaskManager 在完成登记后抛异常，Scheduler 会扣回负载，却保留任务记录与 ASSIGNED 状态。现有 failureAfterRecordingCurrentlyRollsBackOnlyWorkload 测试直接刻画了此行为。它依赖故障注入，不意味着当前内存登记普通调用必然这样失败，作为扩展契约不足和后续建议处理，不据此机械压到 7 分以下。应声明登记方法失败时的状态保证，并让补偿与该保证匹配。回滚异常遮蔽原异常、包装丢失 cause 也应改善；不要求为了本题捕获任意 Error。

### 3. 任务列表快照尚未与写入统一协调

TaskManager 在 compute 内修改 ArrayList，但 getTasksByEmployee 在 compute 外执行 List.copyOf，并发时不能保证一致快照。EmployeeManager 的注册、列表快照与极值查询现在已使用同一把锁，这部分旧问题已修复。

任务查询应与同员工登记共用协调机制，或在写入时替换不可变列表。如果只在全部调度结束后查询，可明确该生命周期；当前演示程序采用这一顺序，因此不将未承诺的实时报告能力作为主要扣分项。
