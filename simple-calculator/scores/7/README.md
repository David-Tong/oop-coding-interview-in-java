## 相比 6 分版的进步

- ExecutionContext 统一持有状态和历史，命令不再接触两个 Stack。
- Command 不再保存快照，操作描述与执行记录分离。
- execute 返回 void，消除了既修改原栈又返回其他栈的混合接口。
- 快照复制集中实现，不再需要 clone 强转。
- save 已移到 Calculator，普通命令不必自行调用。
- 删除基类中含义不清的 undo(context)。
- fetchOperands 在弹出前检查数量，不足时不损坏操作数。
- 结果读取改为 peek，getResult 不再消费结果。

## 核心问题

### 1. 双次撤销依赖调用顺序

Calculator.execute 对每条命令都先 save，包括 U。UndoCommand.execute 因此必须 undo 两次：一次抵消刚保存的状态，一次撤销最近的普通操作。

正常表达式可以得到正确结果，但命令依赖调度器额外保存这一细节。直接执行 UndoCommand，或者调度器改为跳过 U 的保存，它就会多退一步。应明确普通操作与撤销控制指令的不同执行规则，而不是让双方相互补偿。

### 2. 操作数不足不变，但失败仍进入历史

输入 7 后按 Calculator 协议先 save，再执行 +。fetchOperands 检查失败，7 得以保留，但多出的快照没有撤销。随后直接 undo 恢复的仍是 7，而不是输入 7 之前的空状态。

因此不能将“数量检查通过改进”描述成“操作数和历史均保证失败一致性”。自定义命令若先 pop 再抛异常，当前状态仍会损坏，也没有统一恢复入口。

### 3. 生命周期不明确

Calculator 保存同一 context，重复 execute 会重新执行所有命令并累积状态。Calculator("1") 第一次返回 1，第二次最终有两个操作数，抛出结果异常。应每次求值创建新上下文，或明确限制一次执行。

### 4. 空历史及错误信息

ExecutionContext.undo 直接 pop，没有语义化的边界检查。底层 EmptyStackException 缺少原因。严格输入边界也未补齐，`1,` 仍会被接受。后者属于后来题目补充的要求，不追溯改动此前评分范围。
