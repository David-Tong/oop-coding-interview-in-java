# 评审：8/10

本目录名称为 `9`，本次对实际实现的统一评分为 **8/10**。评分沿用仓库的核心功能与 OOP 口径；当前题目新增的严格输入要求单独列出，不追溯改变评分范围。

## 总体评语

实现已经形成比较清楚的解析、运算、执行和历史管理职责。普通命令不再接收整个 Engine，只根据输入计算结果，减少了命令修改历史或嵌套调度的机会。ExecutionContext 集中管理快照，保留初始空状态，并在恢复和撤销时复制容器，核心计算及撤销路径是可靠的。

距离 9 分的主要差距在于接口契约和验证完整性。Command 的统一执行方法并不适用于所有子类，Engine 又通过具体类型识别可执行命令，导致类型声明与实际行为不一致。重复执行的生命周期仍未明确，失败恢复测试也尚未落实。因此，这次重构改善了权限边界，但还没有形成足够自洽、容易验证的完整接口模型。

## 做得好的地方

- AddCommand 和 SubCommand 只接收左右操作数，减法顺序明确，不持有可变执行状态。
- ExecutionContext 集中管理当前操作数和历史，命令不直接接触快照。
- 保留初始空快照，支持撤销第一个数字及连续撤销。
- 恢复、提交和撤销均复制状态，避免后续操作修改历史快照。
- 结果读取使用 peek，不改变计算状态。

## 主要改进点

### 1. 让命令类型与执行入口匹配

Command 要求所有子类实现无参 execute()，但加减命令及 UndoCommand 都通过抛出 UnsupportedOperationException 实现这个方法。这意味着使用者不能按照基类承诺统一执行命令。

Engine 同时依赖 instanceof BinaryCommand、NumberCommand 和 UndoCommand 进行分派。传入其他合法的 Command 子类时，Engine 不调用它的 execute()，却仍然 commit，形成静默忽略操作、增加历史的行为。

建议明确表达数字、二元运算与撤销的不同能力，并使执行器对支持的类型进行完整分派。若允许扩展命令，应给出有效的执行协议；若只支持固定类型，应在类型层面限制范围，或明确拒绝不支持的命令。

### 2. 明确执行对象的生命周期

Calculator 和 Engine 保留执行状态，却没有重置或拒绝重复执行。实测同一个 Calculator("1") 首次返回 1，第二次执行因操作数累积而报最终栈错误。

可以选择每次求值创建独立状态，也可以明确采用一次性对象并在再次执行时抛出清楚的生命周期异常。当前行为不能表达这两种契约中的任何一种。

### 3. 补上有效的失败一致性测试

TestEngine.shouldRestoreStateWhenCommandFailsAfterMutation() 当前是空方法。它会被测试框架计为通过，但没有验证任何行为。

应覆盖：部分弹出操作数后失败，操作数恢复；失败不增加或消耗撤销历史；失败后仍可继续接收操作；空历史撤销失败不破坏后续操作。若 Engine 选择整批执行 API，也应说明如何提供并验证题目要求的单操作失败后继续执行能力。

### 4. 补齐当前题目的输入和错误说明

- split(",") 丢弃尾部空 token，导致 `1,` 和 `1,,` 被接受，应保留并校验空 token。
- null 输入缺少明确校验，会触发底层 NullPointerException。
- 操作数不足时抛出的 EmptyStackException 没有消息，不符合错误需说明原因的要求。
- 最终结果数量错误可以直接说明实际操作数数量，使调用者容易定位原因。

这些是当前完整验收的缺口，其中严格输入要求按仓库约定单独记录。
