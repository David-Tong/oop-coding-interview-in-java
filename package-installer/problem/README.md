# 支持依赖解析的软件包安装器

## 任务

使用 Java 17 实现一个内存中的软件包安装器，并编写 JUnit 自动化测试。安装仅表示更新内存中的已安装集合，不实际下载、执行脚本或操作文件系统。

建议练习时间为 60–90 分钟，仅供控制范围，不作为评分硬性条件。

## 软件包目录

构造安装器时传入固定的软件包目录。每个软件包包含名称和有序的直接依赖名称列表，不处理版本。

- 名称区分大小写，不得为 null 或全空白，按原字符串精确比较，不自动去除首尾空白。
- 目录、软件包记录、依赖列表及其中的名称均不得为 null。
- 包名不得重复。同一个包的依赖列表中，同一名称不得重复。
- 允许空目录和空依赖列表。
- 目录可以包含不存在的依赖及循环依赖，不要求构造时验证这些图问题；仅在规划或安装涉及它们时报告错误。
- 构造后目录固定。调用者修改原始输入容器，不得改变安装器行为。

## 必须支持的操作

自行设计 API，至少提供下列能力：

### 1. 查询安装计划

给定一个目标包，返回当前尚未安装、为安装该目标所需新增的包名列表。

顺序必须确定：从目标开始，按每个包声明的依赖顺序依次深入；处理完一个包的全部依赖后，再将该包加入计划。共享依赖只出现一次。

已安装的包及其依赖不再次展开，也不出现在新增计划中。目标已安装时返回空计划。

查询不改变已安装状态。目标不存在、遍历到不存在的依赖或发现循环依赖时，应明确报错。无关分支的目录错误不影响本次查询。

### 2. 安装

给定目标包，解析并安装所需的软件包，返回本次新增安装的包名列表，顺序与查询计划一致。

一次安装必须整体成功或整体失败：即使已经遍历过若干合法依赖，只要后续遇到缺失依赖或循环，已安装集合也必须与调用前完全相同。

重复安装已安装的目标返回空列表，是成功的无变化操作。

### 3. 卸载

只卸载指定包，不自动清理它的依赖。

- 指定包必须已经安装，否则报错。
- 若仍有已安装的包直接依赖它，应拒绝卸载，并保持状态不变。
- 成功卸载后允许重新安装。

### 4. 查询已安装集合

返回当前已安装的包名集合，不要求顺序。读取不能改变状态，调用者不能通过返回值修改内部集合。

## 示例

目录如下，方括号顺序就是声明顺序：

```text
app  -> [web, db]
web  -> [core]
db   -> [core]
core -> []
tool -> [core]
```

新安装器初始没有已安装包。

| 操作 | 结果 |
| --- | --- |
| 查询 app 的安装计划 | `[core, web, db, app]`，状态仍为空 |
| 安装 tool | 新增 `[core, tool]` |
| 查询 app 的安装计划 | `[web, db, app]` |
| 安装 app | 新增 `[web, db, app]` |
| 再次安装 app | 新增 `[]` |
| 卸载 core | 失败，有已安装包依赖它 |
| 卸载 app | 成功，web、db 等仍保持安装 |

另一个目录：

```text
broken -> [core, missing]
core   -> []
loop-a -> [loop-b]
loop-b -> [loop-a]
```

在空状态安装 broken 应因 missing 不存在而失败，core 也不能留下；安装 loop-a 应报告循环，并保持空状态。随后安装 core 应成功。

## 一致性和错误处理

- 非法输入、未知目标、缺失依赖、循环依赖、卸载限制应报错，消息说明原因，不要求固定异常类型或文案。
- 循环错误至少包含一个涉及循环的包名；不强制输出完整环路径。
- 查询计划及所有失败操作不改变已安装状态。
- 每个实例维护独立的已安装状态。操作失败后，仍可继续查询、安装或卸载。
- 不要求并发、外部安装失败回滚或用户可扩展回调。

## 交付要求

1. Java 17 实现和 JUnit 自动化测试，提供可重复执行的构建命令。
2. 合理组织软件包描述、依赖解析及安装状态管理职责，封装输入与输出中的可变容器。不强制使用设计模式或特定类名。
3. 测试覆盖依赖链、共享依赖、依赖声明顺序、重复安装、缺失依赖、自依赖与多节点循环、失败不留下部分安装、卸载限制、失败后继续操作，以及实例隔离。
4. 简要说明主要 API、设计取舍及复杂度。请定义复杂度中的节点和边表示什么。

不要求版本约束、批量目标安装、自动清理、并行安装、持久化或最优数据结构。
