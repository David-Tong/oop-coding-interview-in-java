# 单会议室预订器：完整需求

## 1. 要实现什么

使用 Java 17 实现一个管理“某一天的一间会议室”的内存程序，并编写 JUnit 自动化测试。

程序初始没有任何预订，必须支持五个操作：创建预订、取消预订、修改预订时间、列出预订、查找最早的连续空闲时间段。

一个实例可以连续接收多次操作并保留预订状态，不同实例之间状态独立。不需要界面、命令行解析、日期、时区、数据库、网络或并发。

## 2. 预订记录与时间含义

每条预订包含三个字段：

| 字段 | 含义 | 谁提供 |
| --- | --- | --- |
| id | 这条预订的唯一标识，例如 `meeting-A` | 调用者提供，程序不生成 ID |
| start | 这条预订开始占用会议室的时间 | 调用者提供 |
| end | 这条预订结束占用会议室的时间 | 调用者提供 |

时间用当天的整数分钟表示。例如 60 表示 01:00，90 表示 01:30，1440 表示当天结束。

预订时间必须满足 `0 <= start < end <= 1440`，表示半开区间 `[start, end)`。会议室从 start 开始被占用，到 end 时已经释放。

- `[60, 90)` 与 `[90, 120)` 可以同时存在，首尾相接不冲突。
- `[60, 90)` 与 `[89, 100)` 不能同时存在，有一分钟重叠。
- 完全相同、一个区间包含另一个区间，也都属于冲突。

所有接收 ID 的操作都遵循以下规则：

- ID 不得为 null、空字符串或全空白字符串。
- 使用原字符串的 `String.equals()` 判断是否是同一个 ID，不自动 trim，不忽略大小写。
- `meeting-A`、`meeting-a`、` meeting-A ` 是三个不同 ID。
- 判断“重复 ID”是与当前已经保存的预订 ID 比较；取消和改期也用这个规则查找已有记录。

## 3. 五个必须实现的操作

下面的方法名和返回类型只是 API 示例，可以自行设计等价 API。成功的修改操作不强制返回内容；错误通过异常报告，消息需说明原因，不要求固定异常类型或文案。

### 操作一：创建预订

示例：`book(id, start, end)`。

输入是调用者给出的预订 ID 和具体占用时间，程序验证后保存一条预订记录。

成功条件：ID 合法且当前未使用、时间合法、时间段与所有已有预订均不冲突。

失败条件：非法 ID、重复 ID、非法时间、时间冲突。失败时不能留下任何新记录。

例如 `book("A", 60, 90)` 表示保存 ID 为 A、占用 `[60, 90)` 的预订。

### 操作二：取消预订

示例：`cancel(id)`。

按 ID 查找并删除已有预订。非法 ID 或找不到预订时报错。

成功取消后，原来占用的时间释放，这个 ID 也可以重新用于创建预订。

### 操作三：修改预订时间

示例：`reschedule(id, newStart, newEnd)`。

按 ID 找到已有预订，将其时间改为新的时间段，ID 保持不变。

- 非法 ID、找不到预订、非法时间、与其他预订冲突时，都应报错。
- 检查冲突时排除正在修改的这条预订本身。
- 改为与原来相同的时间是成功的无变化操作。
- 任何失败都必须保留原预订的 ID 和时间，不能先删除原记录后丢失它。

### 操作四：列出当前预订

示例：`listBookings()`。

返回所有当前预订，每条包含 ID、start、end，按 start 升序排列。没有预订时返回空集合。

读取不改变状态。调用者不能通过修改返回的集合或其中的记录来改变程序内部状态；可以返回不可变数据，也可以返回独立副本。

### 操作五：查找最早连续空档

示例：`findEarliestSlot(from, to, duration)`，可用 `OptionalInt` 表示结果。

这是一个查询，输入包含三个参数：

| 参数 | 含义 |
| --- | --- |
| from | 允许安排会议的最早时间 |
| to | 会议必须结束的最晚时间 |
| duration | 需要连续空闲多少分钟 |

**from 和 to 只是查找范围，不是要创建的预订的开始和结束时间。** 程序需要在这个范围内，找出一段足够长的连续空闲时间。

返回最早可行的开始时间 s，使 `[s, s + duration)` 完全位于 `[from, to)` 中，并且不与任何已有预订冲突。不能把多段不连续的空闲时间拼起来。

- 参数必须满足 `0 <= from < to <= 1440`、`1 <= duration <= 1440`，否则报错。
- 找不到满足条件的连续空档时，返回“无空档”，例如 `OptionalInt.empty()`。这是正常结果，不抛异常。
- duration 合法但大于查询范围长度时，返回无空档。
- 空档可以恰好从 from 开始，也可以恰好在 to 结束。
- 查询只返回开始时间，不创建预订、不占用会议室。若调用者想预订该空档，需要另行调用创建预订操作。

例如已有 A 占用 `[60, 90)`，B 占用 `[120, 150)`：

```text
查询范围： [70, .................................., 180)
已有占用： [70,90)          [120,150)
连续空档：        [90,120)             [150,180)
空档长度：          30 分钟               30 分钟
```

- `findEarliestSlot(70, 180, 30)` 返回 90，对应可预订的 `[90, 120)`。
- `findEarliestSlot(70, 180, 31)` 返回无空档，两段各 30 分钟不能拼成 31 分钟。
- 空预订器调用 `findEarliestSlot(0, 1440, 1440)` 返回 0。

## 4. 全局一致性要求

- 所有失败操作都必须保持已有预订集合完全不变，失败后仍可继续接收操作。
- 查询操作不能修改状态。
- 不同实例之间不能共享可变预订状态。
- 不要求同时触发多个错误时按特定顺序检查，报告其中一个明确的错误即可。

## 5. 连续操作示例

以下操作按行依次执行，不是互相独立的测试：

| 步骤 | 操作 | 预期结果 |
| --- | --- | --- |
| 1 | 创建 A，时间 `[60, 90)` | 成功 |
| 2 | 创建 B，时间 `[120, 150)` | 成功 |
| 3 | 在 `[70, 180)` 中查找连续 30 分钟空档 | 返回 90，不改变预订 |
| 4 | 在 `[70, 180)` 中查找连续 31 分钟空档 | 无空档，不改变预订 |
| 5 | 将 A 改为 `[100, 130)` | 与 B 冲突，失败；A 仍为 `[60, 90)` |
| 6 | 将 A 改为 `[90, 120)` | 成功，与 B 首尾相接 |
| 7 | 取消 B | 成功，现在只有 A 占用 `[90, 120)` |
| 8 | 在 `[70, 180)` 中查找连续 60 分钟空档 | 返回 120 |

## 6. 交付与评审范围

将实现和测试放在本题 `solution/` 下，并提供：

1. Java 17 实现与 JUnit 测试，以及可重复执行的构建命令。
2. 简要 API 使用说明、设计取舍和各操作的时间、空间复杂度。
3. 测试覆盖五个操作、非法输入、重复和未知 ID、首尾相接、包含及部分重叠、改期失败保留原记录、空档恰好放下及放不下、查询范围边界、失败后继续操作、返回数据隔离和实例隔离。

不强制类名、容器或设计模式。不要求多会议室、重复会议、撤销、候补队列或最优数据结构，可以假设一天内预订数量很少。

建议练习时间 60–90 分钟，仅供控制范围，不作为评分硬性条件。评分考察正确性、失败一致性、OOP 职责与封装、可读性和测试证据。
