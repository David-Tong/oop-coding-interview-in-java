## 核心问题与复现

### 1. 空档查询漏掉首条及后续预订

BookingManager.findEarliestSlot 使用 floor 查找 from 前面的记录。from 早于第一条记录时，current 为 null；实现没有转向第一条记录，直接跳过扫描并返回 from。

已有 A `[60,90)`、B `[120,150)`：

- `(20,200,50)` 应返回 150，实际返回 20，对应 `[20,70)` 与 A 重叠。
- `(20,150,50)` 应返回 -1，实际也返回 20。

原有 findsSlotBeforeFirstBooking 测试只查 duration=40，恰好能在第一条前放下，因此没有暴露缺陷。

### 2. 改期漏查自身后的邻居，失败会删除原记录

仍用 A、B，执行 `reschedule(new Booking("A", 50, 130))`：

1. floor(50) 为空，ceiling(50) 是原 A。
2. canReserve 因 ID 相同跳过 A，却没有继续检查 B，错误地判定可改期。
3. cancel 删除原 A。
4. reserve 再次检查，发现 B 冲突，返回 false。
5. reschedule 抛异常，但 A 已经丢失，列表只剩 B。

这里 try/catch 没有提供回滚。正确方向是完整检查所有其他记录，再一次提交替换；如果保留邻居算法，跳过自身后必须继续找真正邻居。不要依赖先 cancel 再 reserve 来保证原子改期。

### 3. 可变记录泄露并破坏双索引

Booking 的 Lombok `@Data` 生成 setter。reserve 直接存入调用者的对象，listBookings 只复制列表，元素仍是内部对象。

修改传入对象或返回对象即可改变内部时间与 ID。TreeSet 依赖比较字段保持稳定，原地修改 start/end 会破坏排序与查找；修改 ID 又会使 Map 的键与 Booking.id 不一致，进而影响取消。这是封装与数据一致性问题，不能只用 new ArrayList 修复。

建议不可变 record，或存入和返回均复制。dict、bookings 也应 private，避免包内绕过规则修改。

### 4. 输入校验不统一

- BookingValidator 只检查 ID 和 start<end，接受负时间与 end>1440。
- BookingService.reschedule 没有调用 validator，可以把 A 改成 `[90,60)`。
- findEarliestSlot 没有验证查询范围及 duration，非法参数会作为正常结果处理。
- null Booking 直接解引用。它属于对象式 API 的补充健壮性问题，不作为主要扣分依据。

应为所有修改入口和查询建立一致的校验规则。Service 若是公共边界应完整校验；Manager 若也公开，应明确自己的前置条件，避免两层出现不同有效性规则。

### 5. 错误契约与可读性

题目要求冲突通过异常报告，当前创建和部分改期冲突返回 false。返回 false 可以是另一种合理 API，但不符合本题已声明契约；评审把这两项单独列出，其严重性低于返回错误空档和丢记录。即便接受 false 契约，前述核心缺陷仍成立。

reserver 拼写可改成 reserve；没有处理逻辑的 catch 后原样 throw 可以删除。cancel 的包装异常丢失原始 cause。Service 目前大部分只是转发，Validator 也没有完整使用；优先修复不变量，无需增加更多层或设计模式。
